## Important
1. **`.claude/hooks/agent-guard.mjs:62-82` — le continuateur de ligne contourne le contrôle des options.** [constaté] `splitSegments` coupe sur `\n` sans rejoindre `\` + retour à la ligne (Bash) ni l'accent grave + retour à la ligne (PowerShell). Avec le projet lié = dev, `supabase db push \` + saut de ligne + `--db-url postgres://x` sort en code 0 (autorisé), pour Bash et PowerShell. Même cause pour `--project-ref`, `--workdir` et `--remote=<autre ref>` placés après la coupure. Critère de la spec (« `--db-url`, `--project-ref`, `--workdir` : refus ») non tenu pour cette forme. Correction : retirer `\\\r?\n` et `` `\r?\n `` de la commande avant la découpe, puis ajouter le cas aux tests.
2. **`.claude/hooks/agent-guard.mjs:10` — `npx supabase@<version>` échappe au garde.** [constaté] `SUPABASE_BIN` exige exactement `supabase` : `npx supabase@latest db push --remote` et `npx -y supabase@3.0.0 db push --remote` sortent en code 0 avec un projet lié = prod. C'est la façon courante de lancer une version précise (le journal de T1b parle de « CLI 3.0.0 via npx »). Correction : accepter `supabase(@[^/\\\s]+)?` (et un `pnpm dlx` / `bunx` équivalent passe déjà).
3. **`.claude/hooks/agent-guard.mjs:95-96` — commandes qui appliquent des migrations sans être gardées.** [constaté] CLI 3.0.0 (`supabase migration --help`) : `migration up` (« Apply pending migrations to a database [local or remote] »), `migration down` (« Resets applied migrations »), `migration squash`, `migration fetch` ciblent un hébergé via `--remote`. `migration up --linked` avec un lien prod sort en code 0. `migration up --remote` fait la même chose que `db push`. La spec ne cite que `db push|reset|query` et `migration repair`, mais le garde perd son sens si l'équivalent direct de `push` passe. Correction : ajouter `migration up|down|squash`.
4. **`.claude/hooks/agent-guard.mjs:108-167` — pas d'échec fermé sur exception.** [constaté] Aucun `try/catch` global : une entrée `null` sur stdin (`JSON.parse('null')` réussit, puis `input.tool_name` lève) sort en **code 1** ; or tout code autre que 2 est une erreur non bloquante côté Claude Code, et la commande s'exécute. Atteignable seulement avec une entrée de hook malformée [supposé : le harnais envoie toujours un objet], mais c'est l'exigence formulée (« une exception ne doit pas laisser passer la commande »). Correction : envelopper la partie logique dans `try { … } catch { deny('erreur interne du garde') }` et traiter `typeof input !== 'object' || input === null` comme refus. Ajouter un test.
5. **`supabase/migrations/20261105_helloasso_grants_explicites.sql:36-39` — droits plus larges que `server/`.** [constaté] `grep` : `server/` n'utilise que `helloasso_tokens` (`readRow` SELECT, `writeAsHolder` et `invalidate` UPDATE, RPC `helloasso_acquire_token_lock`) ; **aucune** référence à `helloasso_sync_runs` dans `server/` ni `app/`. La spec D dit « `service_role` : uniquement ce que `server/` utilise ». D accorde pourtant SELECT, INSERT, UPDATE sur `helloasso_sync_runs`. La migration le justifie par la synchronisation à venir (point déjà noté « à arbitrer » dans `status.md`). Décision à prendre : (a) garder (anticipation) et l'écrire dans la spec, ou (b) n'accorder que ce qui sert, et ajouter les droits avec la migration du lot qui écrira la table. Corollaire [constaté] : `docs/mise-en-prod.md` § 3 étape 10 demande de vérifier « le passage dans `helloasso_sync_runs` » après la première synchronisation ; aucun code ne l'alimente aujourd'hui, la vérification échouerait. Pas de `DELETE` nécessaire : aucun `.delete()` ni `.upsert()` de `server/` ne vise ces tables [constaté] (les `.upsert()` visent `profiles` et `profile_payments`, le `.delete()` du webhook vise `profile_payments`).
